# Nyx — Приватный офлайн-дневник — Архитектурная спецификация

Название проекта: **NyxD** (от Νύξ, греческой богини ночи — отсылка к сценарию использования "заметки перед сном" + Diary).

Статус: согласовано, готово к реализации.
Стек: Flutter (Dart) + SQLCipher.
Модель угроз: защита от казуального/физического доступа к устройству (кража, потеря телефона, посторонний с доступом к разблокированному устройству). НЕ рассчитано на противодействие государственным/лабораторным атакам (Cellebrite и т.п.) — это осознанно избыточно для задачи.

Главный принцип: стоимость взлома должна быть выше ценности содержимого дневника.

## 1. Криптографический конвейер

### 1.1 Цепочка "пароль → ключ"

1. Пользователь вводит мастер-пароль (UTF-8 строка).
2. Нормализация строки — Unicode NFKC (важно для консистентности при вводе на разных раскладках/языках).
3. Argon2id с уникальной солью → 256-битный ключ.
4. Ключ передаётся в SQLCipher как **raw key** (не как passphrase — избегаем повторной внутренней KDF SQLCipher).

### 1.2 Соль

- Генерируется криптографически стойким RNG при первом создании базы (при onboarding).
- Хранится в открытом виде рядом с БД (не секрет — задача соли: уникальность деривации и защита от rainbow tables).

### 1.3 Параметры Argon2id

Целевое время деривации: **0.5–1 сек** на среднем ARM-устройстве (Cortex-A76 класс).

Ориентировочные параметры:
- Memory (m_cost): 64–128 MiB — основной параметр защиты от GPU-перебора (у GPU мало быстрой памяти на ядро)
- Iterations (t_cost): 2–3
- Parallelism (p_cost): 2–4

**Обязательно:** калибровка на первом запуске — замерить реальное время деривации на конкретном устройстве и адаптировать параметры (по аналогии с Signal/Bitwarden), чтобы на слабых бюджетных SoC не было неприемлемого фриза.

**Обязательно:** деривация выполняется в отдельном Isolate, никогда не в UI-потоке.

### 1.4 Библиотека

По результатам технического прототипа используется `cryptography` 2.9.x. Пакет предоставляет актуальную реализацию Argon2id и совместим с используемой версией Flutter/Dart. Деривация обязательно запускается через отдельный Dart Isolate.

Изначально рекомендованный `dargon2_flutter` не выбран: опубликованная версия не обновлялась несколько лет и создаёт лишний риск совместимости с современным Flutter toolchain. Возврат к нативному FFI-биндингу возможен, если замеры на реальных ARM-устройствах покажут недостаточную производительность текущей реализации.

### 1.5 Очистка ключа из памяти

- Ключ хранится только в `Uint8List` (не в `String` — строки в Dart иммутабельны и могут "размножаться" в памяти).
- Явное зануление (`fillRange(0, len, 0)`) при уходе в фон.
- При `AppLifecycleState.paused/inactive/detached` — не только зануление ключа, но и **полное закрытие соединения SQLCipher**.

Честное ограничение: защита от дампа памяти *работающего* процесса в managed-рантайме (Dart VM) — best effort, не гарантирована. Полная защита от cold storage forensics — да, от live memory dump — нет. Это ограничение модели угроз, не implementation detail.

## 2. Архитектура базы данных

### 2.1 SQLCipher

Вся БД шифруется на уровне страниц через SQLCipher. **Не** шифровать отдельные поля дополнительно — избыточно.

Библиотека: `sqlite3` 3.x с native hook `source: sqlcipher`. Отдельный пакет `sqlcipher_flutter_libs` больше не используется, так как он объявлен EOL для `sqlite3` 3.x.

Raw key передаётся SQLCipher как 64-символьный hex blob через `PRAGMA key = "x'…'"`, что отключает внутреннюю парольную KDF SQLCipher. После установки ключа приложение обязано проверить `PRAGMA cipher_version` и выполнить чтение `sqlite_master`.

⚠️ Ограничение биндинга: SQL-интерфейс `PRAGMA key` требует кратковременного создания hex-строки ключа. Это противоречит идеальной модели «только `Uint8List`», поскольку строки Dart иммутабельны. На этапе криптографического ядра необходимо отдельно оценить вызов нативного `sqlite3_key` через FFI либо явно принять это как best-effort ограничение managed-рантайма.

### 2.2 Структура таблиц

**entries**
- `id`
- `created_at` (unix timestamp в миллисекундах, UTC)
- `updated_at`
- `content` (текст заметки, полный)
- `deleted_at` (nullable — для soft delete / корзины)

Текущая версия схемы: **2**. Версия хранится в служебной таблице `vault_info`; миграции выполняются последовательно внутри транзакций.

Заголовок заметки — **не отдельное поле**, а первая строка `content`, вычисляется на лету при отображении списка.

**Теги — без отдельной таблицы.**
Теги парсятся из текста заметки по паттерну `#слово` (regex) при отображении/сохранении. Отдельная таблица `tags` и связующая `entry_tags` не нужны — упрощение по сравнению с первой версией архитектуры, продиктовано референсным UI (см. раздел 5).

### 2.3 Проверка пароля

SQLCipher проверяет ключ "из коробки" через HMAC при первом чтении (`PRAGMA key` + `SELECT count(*) FROM sqlite_master`). Отдельный заголовок не нужен.

⚠️ Важно понимать: это даёт атакующему детерминированный оракул для офлайн-перебора на украденном файле. Вся стойкость держится на дороговизне Argon2id (раздел 1.3), а не на архитектуре заголовка — это неустранимо при разумном UX.

### 2.4 Поиск и индексы

FTS5-индекс по content создаёт потенциальный побочный канал утечки статистики текста. Решение по умолчанию: **без персистентного полнотекстового индекса**, поиск — по расшифрованным данным "на лету" в памяти.

## 3. Защита на уровне Android OS

Обязательные флаги/настройки в проекте:

- `android:allowBackup="false"` — запрет системных бэкапов (иначе `adb backup`/облачный бэкап производителя может выгрузить БД в обход шифрования на уровне приложения)
- `android:fullBackupContent` с явным исключением директории БД — defense-in-depth поверх allowBackup
- `FLAG_SECURE` на Activity — запрет скриншотов и превью в списке недавних приложений
- Файлы БД и метаданные (соль) — строго во внутренней приватной директории (`context.filesDir`), НЕ на `getExternalFilesDir`

### Android Keystore — решение: НЕ используем

Обсуждался вариант привязки ключа к аппаратному Keystore (StrongBox) как дополнительный слой защиты. **Отклонён**, так как несовместим с требованием переносимости БД между устройствами (пользователь явно хочет переносить заметки при смене телефона). Ключ выводится полностью из пароля, без аппаратной привязки.

### Duress Password (ложный пароль) — решение: НЕ реализуем

Обсуждался концепт второго пароля с фейковым хранилищем. Отклонён как избыточный для модели угроз "не Сноуден" — настоящая plausible deniability труднодостижима в одноприложенческой реализации, а польза не оправдывает сложность. Не входит в скоуп.

## 4. UX-логика безопасности

### 4.1 Неверный пароль

UI показывает явную ошибку "неверный пароль". Без искусственной задержки поверх Argon2id — задержка уже встроена в саму деривацию (~1 сек на попытку).

### 4.2 Автоблокировка

- При сворачивании приложения (`paused`/`inactive`/`detached`) — БД закрывается немедленно, ключ зануляется.
- Таймер бездействия **30–50 секунд**: если приложение открыто, но нет действий пользователя — автоматическая блокировка (закрытие БД, возврат на экран ввода пароля), даже без сворачивания.

### 4.3 Onboarding (первый запуск)

- Экран создания мастер-пароля с **двойным вводом** (подтверждение).
- Явное, недвусмысленное предупреждение: восстановления пароля нет, при утере данные будут потеряны безвозвратно. Пользователь должен осознанно это подтвердить перед созданием.

### 4.4 Резервное копирование (Backup/Export)

Отдельная функция ручного экспорта: пользователь может сохранить копию зашифрованного файла БД (например, на внешний накопитель или в выбранную папку) на случай потери/поломки устройства без предварительного переноса. Экспортируется тот же зашифрованный файл — без дополнительного отдельного шифрования при экспорте.

### 4.5 Корзина (soft delete)

Удаление заметки — мягкое: проставляется `deleted_at`, запись не удаляется физически сразу. Отображается в отдельном разделе "Корзина" (см. UI, раздел 5).

**Открытый вопрос:** срок автоматической окончательной очистки корзины (например, 30 дней) — требует решения перед реализацией.

## 5. UI/UX референс

Целевой стиль — по референсным скриншотам (минималистичная заметочная app):

- **Главный экран:** плоский список заметок, заголовок = первая строка текста, без превью содержимого, жирный шрифт, белый фон, FAB-кнопка создания новой заметки внизу справа
- **Редактор:** курсор автофокус в поле ввода сразу при открытии (главное UX-требование — быстрый ввод перед сном), тёмная тема, поле "Добавить метку…" внизу экрана
- **Боковое меню:** "Все заметки", "Корзина", "Настройки", раздел "Метки" со списком всех использованных `#тегов`, "Заметки без меток"
- **Метки:** вводятся прямо в тексте заметки как `#слово`, автоматически парсятся и агрегируются в меню — отдельного UI-селектора тегов нет

## 7. Перенос между устройствами

Механизм: ручной **USB-импорт**. Пользователь копирует файл заметки/экспорта с компьютера на телефон через кабель, приложение подхватывает файл из специальной папки импорта и добавляет как новую запись (или, в случае полного экспорта БД — как замену/слияние базы при смене устройства).

Гигиена: исходный незашифрованный файл на компьютере должен удаляться сразу после переноса — это точка риска вне контроля приложения.

## 8. Открытые вопросы (требуют решения перед/во время реализации)

1. Срок хранения заметок в корзине до окончательного удаления.
2. Точный UX-флоу слияния при импорте полного бэкапа БД на новое устройство (замена vs слияние с текущими записями).
3. Формат файла для USB-экспорта отдельной заметки (обычный текст vs что-то структурированное для сохранения метаданных created_at/tags при импорте).
